## 一、这份东西是干什么的

一个 MCP server，让 Claude Code 这类 AGENT **直接使用你的 Linux 桌面**：读界面、点按钮、输入文字、按快捷键。

它和「截图 + 让模型数像素猜坐标」的传统做法不同——**优先读无障碍树（AT-SPI）拿到结构化的界面描述，再用元素级操作去点**。元素级操作不经过坐标，所以不受焦点、分辨率、DPI 缩放影响，从根上没有「点不准」这回事。

拿不到无障碍树的应用（Java/SWT、自绘控件、游戏、远程桌面）退到 **OCR**：把屏幕文字连同坐标一起读出来，模型读文字定位，坐标是算出来的而不是猜的。

**默认在隔离沙箱里干活**：自启一块 Xephyr 虚拟屏，所有点击/输入/截图都落在虚拟屏上，**你的真实桌面不受任何干扰**，你可以在 agent 干活的同时继续用电脑。

## 二、前置条件

| 项 | 要求 | 说明 |
|----|------|------|
| 操作系统 | Linux（Debian/Ubuntu 系命令按此写） | **Windows 已支持**，但走的是另一套安装方式（安装包 + 免管理员），见 [7.8](#78-windows安装包--packagingwindows) |
| 会话类型 | **X11** | `echo $XDG_SESSION_TYPE` 应为 `x11`。Wayland 下全局输入注入受限 |
| 桌面环境 | GNOME（推荐）/ 其他可开 AT-SPI 的环境 | 需要能开无障碍开关 |
| Python | conda 环境，**Python ≥ 3.12** | 环境名 `cc-computer-use`（2026-09-21 前本机误拼为 `cc-comptuer-use`，已用 `conda rename` 改正） |
| 磁盘 | ≥ 1.5 GB | 打包产物本身约 455 MB |

**Python 依赖（装进 conda 环境，不是系统包）**：

| 包 | 用途 | 缺失后果 |
|------|------|----------|
| `python-xlib` | 点击光圈（`backend/linux/ring.py`）——纯 Python 的 X11 客户端，走 socket、不链 `libX11` | 只是**看不见光圈**，坐标点击与其余证据照常（`ring.py` 里是懒 import + 按屏熔断） |

**系统组件（全部是 OS 级依赖，不内嵌进打包产物）**：

| 组件 | 用途 | 缺失后果 |
|------|------|----------|
| `xdotool` | 鼠标/键盘注入、窗口几何查询 | 无法操作，`list_windows` 等失效 |
| `xserver-xephyr` | 隔离沙箱的虚拟屏 | 沙箱起不来，操作被**拒绝执行**（不会静默打到真实桌面） |
| `tesseract-ocr` + `tesseract-ocr-chi-sim` | OCR 灰区感知 | `get_screen_text` 不可用；中文全变乱码 |
| `xclip` | 非 ASCII 文本输入（走剪贴板） | 无法输入中文 |
| `wmctrl` | 应用枚举（读 `WM_CLASS`） | 应用列表功能失效 |
| `zenity` | **仅测试用** | 端到端测试 skip |
| `gir1.2-atspi-2.0` / `libatspi` | 无障碍树读取 | 读不到任何元素树 |

## 三、快速开始（TL;DR）

已经装好依赖、只想跑起来的话：

```bash
# 1) 系统依赖
sudo apt install -y xdotool xserver-xephyr zenity xclip wmctrl \
                    gir1.2-atspi-2.0 \
                    tesseract-ocr tesseract-ocr-chi-sim

# 2) 开无障碍开关（否则读不到 GTK 应用的树）
gsettings set org.gnome.desktop.interface toolkit-accessibility true

# 3) conda 环境
conda create -n cc-computer-use python=3.12 -y
conda install -n cc-computer-use -c conda-forge pygobject -y

# 4) Python 依赖 + 本项目
PY=/home/$USER/anaconda3/envs/cc-computer-use/bin/python
PYTHONNOUSERSITE=1 "$PY" -m pip install -U mcp cryptography pyinstaller pytest python-xlib
cd /path/to/cc-computer-use
PYTHONNOUSERSITE=1 "$PY" -m pip install -e .

# 5) 验证
PYTHONNOUSERSITE=1 "$PY" -m computer_use_mcp.server --selftest
```

装完把 [第六节](#六接入-claude-code) 的配置贴进 `~/.claude.json` 即可用。

## 四、详细安装步骤

### 4.1 系统依赖

```bash
sudo apt update
sudo apt install -y \
    xdotool xserver-xephyr xclip wmctrl zenity \
    gir1.2-atspi-2.0 \
    tesseract-ocr tesseract-ocr-chi-sim
```

装完核对（**这一步别跳过**，后面所有「奇怪地不工作」大半源于缺件）：

```bash
for c in xdotool Xephyr zenity xclip wmctrl tesseract; do
    printf "%-12s " "$c"; command -v "$c" || echo "❌ 缺失"
done
tesseract --list-langs      # 应能看到 chi_sim 与 eng
```

> **`chi_sim` 是简体中文语言包**，不装的话中文界面识别出来全是乱码。`tesseract --list-langs` 里只列了 `eng` 就说明没装。

### 4.2 开启无障碍开关

```bash
gsettings set org.gnome.desktop.interface toolkit-accessibility true
gsettings get org.gnome.desktop.interface toolkit-accessibility   # 应输出 true
```

**不开这个开关，GTK 应用根本不构建无障碍树**，`get_ui_tree` 会返回空——而报错信息不会告诉你原因，只会表现为「读不到界面」。

> 这属于 GNOME 的会话设置，重启后一般保留；但**新建用户 / 重置 dconf 后需要重设**。

### 4.3 conda 环境与 Python 依赖

```bash
conda create -n cc-computer-use python=3.12 -y
```

**`pygobject` 必须走 conda-forge**——它依赖系统的 GLib/GObject 头文件与 typelib，`pip install pygobject` 在多数机器上直接编译失败：

```bash
conda install -n cc-computer-use -c conda-forge pygobject -y
```

其余纯 Python 依赖走 pip：

```bash
PY=/home/$USER/anaconda3/envs/cc-computer-use/bin/python
PYTHONNOUSERSITE=1 "$PY" -m pip install -U mcp cryptography pyinstaller pytest python-xlib
```

> ⚠️ **`PYTHONNOUSERSITE=1` 不是可选项**：`~/.local` 里若装了另一份 `mcp`，它会**遮蔽** conda 环境里的版本，导致导入到错误版本（开发与打包都受影响，且报错信息完全指不到这里）。**凡是调用这个环境的 python，一律带上这个前缀。**

### 4.4 安装本项目

```bash
cd /path/to/cc-computer-use
PYTHONNOUSERSITE=1 "$PY" -m pip install -e .
```

`-e`（可编辑安装）便于改代码后立即生效。注意 `pyproject.toml` 里**没有**声明 `pygobject`（它只能由 conda 提供），所以第 4.3 步不能省。

### 4.5 一次性环境准备小结

到这里，以下这些应当全部成立——这是后续所有功能的地基：

- [ ] `xdotool` / `Xephyr` / `xclip` / `wmctrl` / `tesseract` 都在 PATH 里
- [ ] `tesseract --list-langs` 含 `chi_sim`
- [ ] `gsettings get ... toolkit-accessibility` 为 `true`
- [ ] `$XDG_SESSION_TYPE` 为 `x11`
- [ ] conda 环境 `cc-computer-use` 里 `import gi` 成功，且 `gi.require_version('Atspi','2.0')` 不报错
- [ ] `pip install -e .` 成功

## 五、验证安装

按**由浅入深**的顺序跑，哪一步失败就停在那一步查（见[故障排查](#九故障排查)）。

### 5.1 自检（最快的健康检查）

```bash
PY=$HOME/anaconda3/envs/cc-computer-use/bin/python
PYTHONNOUSERSITE=1 "$PY" -m computer_use_mcp.server --selftest
```

**不进入 stdio 循环**，打印 backend 状态、注册的工具清单、屏幕布局后退出。能正常打印就说明「Python 侧 + AT-SPI + X11」都通了。

> 默认（isolated 模式）这一步会**自启一个 Xephyr 沙箱窗口**，进程退出时自动回收——看到一个虚拟屏窗口弹出来又消失是正常的。
>
> ⚠️ 自检**刻意不走 AT-SPI 应用枚举**（历史事故：枚举宿主应用会把 GNOME Shell 打成 SIGSEGV）。改动时不要把 AT-SPI 的 `list_apps` 加回自检。

### 5.2 单元测试（不需要桌面）

```bash
cd /path/to/cc-computer-use
PYTHONNOUSERSITE=1 "$PY" -m pytest -q
# 预期：541 passed, 9 skipped
```

**不需要**图形会话即可跑。`conftest.py` 会自动把显示模式设成 `real`，避免测试意外弹出一堆 Xephyr 窗口。

### 5.3 端到端测试（需要 X11 + zenity + Xephyr）

```bash
CC_CU_E2E=1 PYTHONNOUSERSITE=1 "$PY" -m pytest -q
# 预期：547 passed, 3 skipped
```

需要显式 opt-in（`CC_CU_E2E=1`），默认在**沙箱内**跑、不碰真实桌面。

不带这个开关时，端到端用例会 skip，结果是 `541 passed, 9 skipped`。两者都应全绿。

### 5.4 手动 story（完整链路，最接近真实使用）

这 **5 个**脚本用 MCP stdio 客户端驱动**真实 server**，跑完整任务链路，退出码 `0` = 全过：

```bash
# 沙箱隔离：起 zenity → 读树 → 元素级点「是」，并断言宿主桌面零干扰
PYTHONNOUSERSITE=1 "$PY" tests/manual_sandbox_story.py

# a11y 私有总线隔离（内含安全闸：确认看不到宿主应用才继续）
PYTHONNOUSERSITE=1 "$PY" tests/manual_a11y_isolation.py

# 灰区感知全链路（OCR）：需先 bash build.sh
PYTHONNOUSERSITE=1 "$PY" tests/manual_ocr_story.py

# 真实桌面 gedit 写文件并保存（刻意的真实桌面链路，非沙箱）
PYTHONNOUSERSITE=1 "$PY" tests/manual_gedit_story.py

# DBeaver a11y 树探针（判定某应用是否属「灰区」时用；需传 DBeaver 的 pid）
PYTHONNOUSERSITE=1 "$PY" tests/manual_dbeaver_a11y_probe.py <dbeaver_pid>
```

> ⚠️ `manual_sandbox_story.py` 运行期间**不要动鼠标键盘**——它断言「宿主活动窗口与指针位置前后不变」，你一晃鼠标断言就失败。

另有 9 个**跑在别处**的（完整清单见 [`../CLAUDE.md`](../CLAUDE.md) 的「测试坑」一节）：
`manual_shell_story.py`（沙箱里操作 shell，**需先打包**）与 `manual_find_prefilter_probe.py`
跑在**本机**；`manual_windows_backend_story.py` / `manual_windows_mcp_story.py` /
`manual_windows_capture_story.py` / `manual_windows_hidden_desktop_probe.py` /
`manual_windows_directed_probe.py` 与 `manual_windows_isolated_story.py`
跑在 **Windows 客体**上（需交互式会话）；
`manual_windows_guards_reverse.py` 在宿主即可跑。

## 六、接入 Claude Code

在 `~/.claude.json` 的顶层 `mcpServers` 中加一项：

```json
{
  "mcpServers": {
    "cc-computer-use": {
      "type": "stdio",
      "command": "/绝对路径/cc-computer-use/dist/computer-use-mcp",
      "args": [],
      "env": {
        "PYTHONNOUSERSITE": "1"
      }
    }
  }
}
```

### 关于名字：用 `cc-computer-use`，不要用 `computer-use`

**实测 `computer-use` 这个名字注册不上**，改用 `cc-computer-use` 即可。名字只影响你在 Claude Code 里看到的标识，功能不受影响。

### 两种接法

**A. 指向打包产物（推荐）**

`command` 填 `dist/computer-use-mcp`（是个 shell wrapper，转发到 `dist/computer-use-mcp-bin/`）。优点：**不需要 conda 环境在 PATH 里**，启动快。前提是先跑过 `bash build.sh`。

**B. 直接跑源码（开发期）**

```json
{
  "mcpServers": {
    "cc-computer-use": {
      "type": "stdio",
      "command": "/path/to/anaconda3/envs/cc-computer-use/bin/python",
      "args": ["-m", "computer_use_mcp.server"],
      "env": {
        "PYTHONNOUSERSITE": "1",
        "PYTHONPATH": "/绝对路径/cc-computer-use/src"
      }
    }
  }
}
```

改了源码想立即生效就用这种，免去每次重新打包。

> **前提**：Claude Code 必须运行在 **X11 图形会话**中。server 是它的子进程，要继承 `DISPLAY` 才能读屏和注入；在纯 SSH / 无图形会话里启动，工具会报 backend 不可用。

### 接入后怎么用

直接说人话就行：

- 「看一下当前窗口有哪些可点的按钮」→ 调 `get_ui_tree`
- 「帮我点这个对话框的『是』」→ 找元素 + 元素级 `click(ref)`，零坐标
- 「在编辑器里输入 hello 并保存」→ `type_text` + `press_key('ctrl+s')`

## 七、打包与分发

### 7.1 打包

```bash
bash build.sh
```

产物：

```
dist/
├── computer-use-mcp-bin/          # onedir 目录，约 455 MB
│   ├── computer-use-mcp-bin       #   真实可执行文件（约 9.5 MB）
│   └── _internal/                 #   打包进来的库
└── computer-use-mcp               # 薄 shell wrapper，转发到上面那个
```

**为什么是 onedir 而不是单文件**：onefile 每次启动都要把自己解压到临时目录，冷启动慢一个量级。wrapper 的存在是为了**保住已经注册进 `~/.claude.json` 的路径**（那里写的是 `dist/computer-use-mcp`）——所以**别删 wrapper**。

> `build.sh` 开头会 `rm -rf build dist`，**每次都是全量重建**，别指望增量。整个过程需要几分钟。

`build.sh` 认两个环境变量，换机器打包时用得上：

| 变量 | 默认 | 作用 |
|------|------|------|
| `ENV_NAME` | `cc-computer-use` | conda 环境名 |
| `CONDA_BASE` | `$HOME/anaconda3` | conda 安装根目录 |

### 7.2 验证产物

```bash
PYTHONNOUSERSITE=1 ./dist/computer-use-mcp --selftest
```

### 7.3 三种分发形态（按目标用户选）

| 形态 | 产物 | 给谁 | 目标机要装什么 |
|------|------|------|----------------|
| **本机开发产物** | `dist/` | 自己 | 全套 OS 依赖（见 7.4） |
| **`.deb`** | `cc-computer-use_<版本>_amd64.deb` | **Ubuntu 22.04+ / amd64 用户** | **什么都不用装**（自包含） |
| **`.mcpb`** | `cc-computer-use-<版本>.mcpb` | Claude Desktop 用户 | 什么都不用装（自包含） |
| **Windows 安装包** | `cc-computer-use-<版本>-setup.exe` | **Windows 10/11 用户** | **什么都不用装**（见 7.8） |

前三者由**容器构建**一次产出（见 7.5），**不要**拿本机 `build.sh` 的 `dist/` 去打包 ——
那是 24.04 基座，随手发的包在 22.04 上会用不了。
Windows 那个是**另一条链路**（PyInstaller 不能交叉编译，必须在 Windows 上构建）。

### 7.4 在别的机器上用「本机开发产物」（老办法，仍然可用）

**必须一起带**：

1. `dist/` 整个目录（wrapper 与 `computer-use-mcp-bin/` 都不能少）
2. 那条 `~/.claude.json` 配置（`command` 改成目标机上的绝对路径）

**目标机器必须自己装**（这些是 OS 级依赖，**没有**打进这个产物）：

- `xdotool`、`xserver-xephyr`、`xclip`、`wmctrl`
- `tesseract-ocr` + `tesseract-ocr-chi-sim`
- `gir1.2-atspi-2.0` / `libatspi`
- 无障碍开关 `gsettings set ... org.gnome.desktop.interface toolkit-accessibility true`

**不需要** conda、不需要 Python——产物自带解释器与依赖库。

### 7.5 打 `.deb`（推荐的分发形态）

```bash
mkdir -p dist
docker run --rm \
  -v "$PWD":/src -v "$PWD/dist":/out/dist \
  -e CC_CU_CHOWN="$(id -u):$(id -g)" \
  -v /tmp/Miniforge3-Linux-x86_64.sh:/miniforge.sh:ro \
  -e CC_CU_MINIFORGE_SH=/miniforge.sh \
  ubuntu:22.04 bash -c 'bash /src/packaging/build-in-container.sh'
```

三个参数都不是可有可无的：

- **挂到容器内的 `/out/dist`（而不是 `/out`）**：脚本的最终产物路径就是它，于是包直接落在
  本仓库的 `dist/` 下（顺便：`dist/` 已在 `.gitignore` 里，68MB 的二进制不会误进版本库）。
- **中间产物走 `/out/work`（容器内，不在挂载点里）**：不这么分的话，容器构建的
  `computer-use-mcp-bin/` 会与 `build.sh` 的同名产物**互相覆盖** —— 两者基座不同
  （22.04 vs 本机 24.04），而 `dist/computer-use-mcp`（已注册的 MCP 启动脚本）正指向那个
  目录，于是「现在跑的是哪个基座」根本看不出来。
- **`CC_CU_CHOWN`（传宿主的 uid:gid）**：容器以 root 运行，写进挂载目录的东西属主是 root。
  包文件本身还能删（删文件只看父目录的写权限），但 `cc-computer-use/` 里那几百个 root
  所有的文件**没有 sudo 删不掉** —— 不传这个变量，就是把 `/tmp` 的麻烦换了个地方。

产物在 `dist/`：

```
cc-computer-use_0.1.0-1_amd64.deb      # 给 Ubuntu 用户（实测 68 MB）
cc-computer-use-0.1.0.mcpb             # 给 Claude Desktop 用户（实测 98 MB）
cc-computer-use/                       # 两者共用的组装目录（server/ + vendor/）
```

**为什么在 ubuntu:22.04 容器里打**：产物要向前兼容 22.04 → 24.04+。24.04 上取到的
那批系统二进制要求 GLIBC 2.38，直接打包会恰好把最低档排除掉。实测打完的包里，
所有 ELF 的最高 `GLIBC_*` 需求是 **2.35**（正好是 22.04 的基线）。

**关于 miniforge**：容器到 github 的连通性会间歇性失败（实测卡到
`Failed to connect ... after 133027 ms`）。上面用 `CC_CU_MINIFORGE_SH` 挂一个**预先下好**
的安装包，完全不碰网络；也可以改用镜像：

```bash
# 没网时先在能上网的机器上下好（实测国内镜像快 16 倍：github ~0.1MB/s vs 清华 ~1.6MB/s）
curl -fL -o /tmp/Miniforge3-Linux-x86_64.sh \
  https://mirrors.tuna.tsinghua.edu.cn/github-release/conda-forge/miniforge/LatestRelease/Miniforge3-Linux-x86_64.sh
# 或让容器自己下（同样支持 CC_CU_MINIFORGE_URL 覆盖成镜像地址）
```

目标机安装：

```bash
sudo apt install ./cc-computer-use_0.1.0-1_amd64.deb
cc-computer-use-doctor        # 逐项体检，出问题它会讲人话
```

`postinst` 会用 `$SUDO_USER` 当场跑一次用户级配置（打开无障碍开关 + 注册到
Claude Code）；另外装了 `/etc/xdg/autostart/` 兜底，覆盖「多用户机器」「先装包后装
Claude Code」这些 postinst 管不到的情形。

**为什么必须由用户级脚本做这两件事**：`postinst` 以 root 运行，而 `gsettings` 写的是走
会话总线的 dconf、`~/.claude.json` 是用户的文件 —— root 写进去只会落在 `/root`，
是「命令成功、完全无效」的那类失败。所以这些交给 `cc-computer-use-setup`（它第一件事
就是**拒绝以 root 运行**）。

打包相关的文件都在 `packaging/deb/` 下，其中 `build-deb.sh` 也可以单独跑：

```bash
bash packaging/deb/build-deb.sh dist/cc-computer-use /tmp/debout
```

### 7.7 专项探针：确认产物里带着本轮修复

上面那十步验的是**安装链路**（装得上、注册得上、a11y 通），它**不会**去调
`launch_app("gnome-terminal")`、也不会往终端里输入长文本——所以「build 时用的是不是
最新源码」它证明不了。这个探针补的就是那一段：

```bash

```

两个判据都刻意**不看工具返回的 ok**（那两个 bug 的特征恰恰是「工具报成功、实际没生效」）：

| 探针 | 做法 | 判据 |
|---|---|---|
| 去单实例参数 | 在 PATH 最前面放一个**假的** `gnome-terminal`（只记录参数，不真开窗） | 子进程**实际收到**的 argv 里有 `--disable-factory` |
| 终端粘贴键 | 起 `xev`，用 `xdotool set_window --class xterm` 把它的 WM_CLASS **改成终端的样子**（不必真装终端） | `xev` 记录的按键里带 **Shift**（即 `ctrl+shift+v`；裸 `ctrl+v` = 修复前的行为） |

> 状态（2026-09-24）：22.04 与 24.04 各跑一遍，**两个探针都通过**。
> 反证也做过：`CC_CU_PASTE_KEY=ctrl+v` 强制退回旧行为 → 探针变红；
> 把应用名换成表里没有的 `gnome-terminal-helper` → 探针确认**没有**被加参数（判据不是恒真）。

### 7.8 Windows 安装包（`packaging/windows/`）

**目标用户**：Windows 10/11 用户。产物是一个 `cc-computer-use-<版本>-setup.exe`，
装完即注册进 Claude Code。

```bash
# 一次构建（宿主驱动 Windows 客体）：备工具链 → 客体冻结 → 打安装包
CC_CU_VM_PASS='<客体密码>' bash packaging/windows/build-windows.sh

# 端到端验收：装 → 自检 → 查注册 → 卸载 → 查注册被摘掉
CC_CU_VM_PASS='<客体密码>' bash packaging/windows/verify-install.sh
```

几点与 Linux 侧**不一样**的，先说清楚：

| | Linux `.deb` | Windows 安装包 |
|---|---|---|
| 装到哪 | `/opt`（root） | `%LOCALAPPDATA%\Programs\cc-computer-use`（**当前用户，不弹 UAC**） |
| 随包外部命令 | 9 个（xdotool / Xephyr / i3 / tesseract…） | **一个都不用** —— Windows 后端零 subprocess，OCR 走系统自带的 `Windows.Media.Ocr` |
| 沙箱隔离 | 有（Xephyr + 私有 AT-SPI 总线） | **有**（隐藏桌面，见下；可用 `CC_CU_DISPLAY_MODE=real` 关掉） |
| 截图范围 | 整块沙箱屏 | **默认只截目标窗口**（`PrintWindow` 按窗口渲染，不受遮挡影响） |
| 注册 | `claude mcp add --scope user` | 同一条命令（由 `cc-computer-use-setup.ps1` 调） |
| 卸载 | `apt remove` | 设置→应用，或开始菜单里的卸载项；**会顺手摘掉注册项** |

**Windows 上「不抢你的鼠标键盘」是怎么做到的**（2026-09-30 起）：

**`launch_app` 启动的应用会落在「隐藏桌面」上** —— 你看不见它、键鼠也碰不到它，
而 agent 照样能读它的界面、点它的按钮、截它的图（真机验证，见
[`../packaging/windows/README.md`](../packaging/windows/README.md)）。
这与 Linux 的 Xephyr 沙箱是**同一个意思**（agent 在另一个地方干活）。

⚠️ 两点如实说明：

  · **看不见就没法自己介入**。Linux 的沙箱是一块看得见的虚拟屏，agent 卡住时你可以
    瞄一眼甚至伸手点两下；隐藏桌面上做不到，只能让 agent 把截图/读树结果回给你。
  · **只能靠坐标点击的软件在隔离模式下做不了**（SWT/Java、自绘控件、游戏）——
    隐藏桌面上没有输入设备，元素级是唯一还能用的通道。
    这类软件请用 `CC_CU_DISPLAY_MODE=real`（那时它会开在你的桌面上，agent 也照旧能操作）。

**除此之外，「不打扰」还靠两条不碰你输入设备的通道**：

agent 不再靠"抢前台 + 挪真实指针"来操作，而是走两条**不碰你输入设备**的通道：

  · **元素级动作**（UIA `InvokePattern` / `ValuePattern`）—— 直接命令某个按钮/输入框，
    零坐标；真机实测**目标窗口在后台时同样生效，且你的前台不变**；
  · **定向投递**（`PostMessage` 到目标窗口的子控件）—— 键盘已实测**后台可用且不打扰**。

⚠️ **诚实边界**：**鼠标的定向投递实测不成立**（四种技法在对话框与主窗口上分别测过，
全失效）。所以「移动鼠标去点某个坐标」这类操作在 Windows 上没有安全的做法 ——
**隔离模式下它被直接拒绝**（2026-09-30 起，见下条），需要不打扰就请用元素级
`click(ref=...)` / `type_text(ref=...)`。滚轮与拖拽同理。

**隔离模式下，坐标级点击/滚动/拖拽/键盘注入一律被拒绝**（可以显式放开）：

理由不是"效果差一点"，而是**字面意义上在动你的鼠标键盘** —— MCP server 进程自己跑在
你的桌面上（跨桌面操作是刻意保留的能力），于是它发出的键鼠事件只可能落到**你的**桌面：
`SetForegroundWindow` 会成功、`SendInput` 会返回 1、agent 那边报的也是"操作成功"，
而你眼前正在被点、字正在被敲进你的编辑器。所以这一类动作**默认拒绝**，并在报错里
给出三条出路（改用元素级 / 改 `CC_CU_DISPLAY_MODE=real` / 显式放开）。
`type_text` 与 `press_key` 是整条拒绝 —— 它们天然是"打给当前焦点"，而隔离桌面上没有
焦点可言，当前焦点**一定是你**。

| 想要的效果 | 怎么做 |
|---|---|
| 不打扰（默认） | 什么也不用设。用元素级 `click(ref=...)`；没有无障碍树的应用在隔离模式下**做不了** |
| 能操作任何软件，但**会占你的鼠标键盘** | `CC_CU_DISPLAY_MODE=real`（应用开在你桌面上，你看得见） |
| 隔离模式 + 仍要坐标级（**会动你的键鼠**） | `CC_CU_ALLOW_GLOBAL_INPUT=1`（只认字面量 `1`）。此时结果里会**响亮标注**"这一下动的是你的键鼠" |

后两个开关改完都要**重启 Claude Code**（MCP server 是常驻进程）。

**截图**默认只截**你正在操作的那个软件**（不是全屏）：这样既不会把你桌面上的其它窗口
送进模型上下文，目标被别的窗口盖住时也照样截得对。要整屏可以显式传 `scope="screen"`。

**目标机上的前置依赖只有一个**：**Git for Windows**（或 PowerShell 7）。

这不是本程序的口味，是 **Claude Code 自己在 Windows 上的硬要求** —— 两样都没有时，
`claude` 命令连 `--version` 都拒绝执行（系统自带的 Windows PowerShell **5.1 不算**，
Claude Code 要的是 PowerShell 7）。缺了它，「注册到 Claude Code」这一步必然失败。
装上 Git for Windows 后重跑开始菜单里的「注册到 Claude Code」即可
（本包会自动找到它并通过 `CLAUDE_CODE_GIT_BASH_PATH` 交给 claude，不需要手工配环境变量）。

改造/排错细节（编码纪律、Inno 的坑、客体环境、十条踩过的坑）见
[`packaging/windows/README.md`](../packaging/windows/README.md)。
结构与守卫：

```bash

PYTHONNOUSERSITE=1 $PY tests/manual_windows_guards_reverse.py         # 35 条反证（守卫真的抓得到吗）
```

## 九、故障排查

### 症状 → 处理速查

| 症状 | 最可能的原因 | 处理 |
|------|--------------|------|
| `get_ui_tree` 返回空 / 读不到任何界面 | 无障碍开关没开 | `gsettings set org.gnome.desktop.interface toolkit-accessibility true` |
| 所有工具报 backend 不可用 | 不在 X11 图形会话中 | `echo $XDG_SESSION_TYPE` 应为 `x11`；确保 Claude Code 在图形会话里启动 |
| `ImportError: No module named 'gi'` | 用了错误的 python（例如 base 环境） | 显式用 `$HOME/anaconda3/envs/cc-computer-use/bin/python` 绝对路径 |
| `pip install pygobject` 编译失败 | 走了 pip 而不是 conda-forge | `conda install -n cc-computer-use -c conda-forge pygobject -y` |
| 导入到错误的 `mcp` 版本 | `~/.local` 里有另一份 mcp | 命令前加 `PYTHONNOUSERSITE=1` |
| `Atspi` typelib 找不到 | 缺 `gir1.2-atspi-2.0` | `sudo apt install gir1.2-atspi-2.0` |
| OCR 读出来的中文全是乱码 | 缺中文语言包 | `sudo apt install tesseract-ocr-chi-sim`，用 `tesseract --list-langs` 确认 |
| OCR 很慢 | 识别语言含中文，或范围是全屏 | 纯英文界面设 `CC_CU_OCR_LANG=eng`；缩小 `region` / 用 `scope='window'` |
| 操作被**拒绝**并提示沙箱不可用 | 缺 Xephyr 或沙箱启动失败 | `sudo apt install xserver-xephyr`；或不想要沙箱就设 `CC_CU_DISPLAY_MODE=real` |
| 「屏幕正被另一个操作独占」 | 同一会话内有并发子 agent 抢屏 | 等前一个操作结束再试——**这是设计行为**，不会排队（排队会导致基于过期界面操作的错误结果） |
| 操作打到了**真实桌面** | 显式设了 `CC_CU_DISPLAY_MODE=real`，或沙箱失效 | 确认环境变量；检查 Xephyr 是否正常 |
| 中文/非 ASCII 输入把键盘搞失灵一下 | `xdotool type` 会临时改写键盘映射 | 已有对策：非 ASCII 自动走剪贴板（xclip + 粘贴键：普通窗口 `ctrl+v`，终端里 `ctrl+shift+v`）。确认 xclip 已装 |
| 打包后运行报 `OPENSSL_3.3.0 not found` | `LD_LIBRARY_PATH` 没前置 conda 的 lib | 用仓库自带的 `build.sh`（已处理好），别手敲 pyinstaller 命令 |
| 打包时构建失败，提示缺 `typer` | 全量收集了 `mcp` 包 | 用 `--collect-submodules mcp.server`（`build.sh` 已固化），排除 `mcp.cli` |
| `~/.claude.json` 里 `computer-use` 注册不上 | 该名不可用 | 改用 `cc-computer-use` |
| 沙箱内应用崩溃，根目录出现 `hs_err_pid*.log` | JVM 加载了打包产物里的库而非系统库 | 已修复：`app_env()` 会剥掉冻结产物的 `LD_LIBRARY_PATH`。若仍出现，说明该剥离逻辑被破坏 |
| 沙箱内应用**读不到无障碍树** | 该应用不是经 `launch_app` 启动的 | 应用必须经 `launch_app`（走 `app_env()`）启动才会连上沙箱私有总线；手动在沙箱里起的应用不会 |
| 日志里出现「发现 N 个**旧格式**的 AT-SPI 总线残留」 | 目录名不含屏号 → 是 2026-09-16 **之前**的版本留下的（`/tmp/cc-cu-at-spi-<随机>`），本工具按设计**不自动删**（无法判断属于哪块屏，删了可能误伤还跑着旧版 server 的别的会话） | 确认没有旧版会话在跑后手动清理：`pkill -f 'cc-cu-at-spi-' ; rm -rf /tmp/cc-cu-at-spi-*`。清理前可先 `ps -eo pid,ppid,cmd \| grep cc-cu-at-spi` 看还有谁在用 |

### 系统级事故排查（历史教训，供参考）

2026-09-14 / 09-15 曾两次把宿主 GNOME Shell 打成 SIGSEGV。根因是**沙箱的 X11 隔离挡不住 AT-SPI**（无障碍走的是会话 D-Bus，不看 DISPLAY）。现已通过**沙箱私有 AT-SPI 总线**从构造上消除：沙箱内应用连私有总线，宿主总线上完全看不到它们。

如果你怀疑又踩到了类似问题：

```bash
# 看崩溃记录（能看到崩溃进程与信号）
grep -E "gnome-shell|computer-use" /var/log/apport.log

# 检查是否有跨会话残留的私有总线目录与孤儿进程
ls -d /tmp/cc-cu-at-spi-* 2>/dev/null
```

正常情况 `/tmp/cc-cu-at-spi-*` 只应在沙箱存活期间存在。MCP server 被**强杀**（会话被 kill）时它的清理逻辑不会运行，可能留下残留。

> ⚠️ **实测注意**：自动清扫（`_sweep_stale_buses`）按 `cc-cu-at-spi-d<屏号>-*` 这个模式匹配，**只清带屏号的目录**。而不带屏号的形式（如 `/tmp/cc-cu-at-spi-ir9k6w3c`）在屏号尚未确定时会生成，**永远不会被扫到**，会长久留存（实测见过一个存活 1 小时以上、带着一个已被 systemd 收养的孤儿 `at-spi2-registryd`）。
> 判断方法：目录名里没有 `-d<n>-` 的就是这类。确认没有别的会话在用它之后，可以手动 `rm -rf`，并 `kill` 掉仍挂着它的 `at-spi2-registryd`。

> **绝不要**为了这个去用 `at-spi-bus-launcher`（它按 `XDG_RUNTIME_DIR` 推导路径，会抢占宿主的 `at-spi/bus_<n>` socket）。真要恢复宿主总线：`systemctl --user restart at-spi-dbus-bus.service`。

## 十、卸载与清理

```bash
# 1) 退出 Claude Code，确保 MCP server 进程已结束（沙箱会一并回收）
pkill -f computer-use-mcp-bin

# 2) 从 ~/.claude.json 删掉 "cc-computer-use" 那一项

PYTHONNOUSERSITE=1 "$PY" -m pip uninstall computer-use-mcp

# 4) 删产物与源码
rm -rf /path/to/cc-computer-use

# 5) 清理可能的沙箱残留（确认没有别的会话在用）
ls -d /tmp/cc-cu-at-spi-* 2>/dev/null && rm -rf /tmp/cc-cu-at-spi-*
```

conda 环境与系统依赖（xdotool/tesseract 等）如无其他用途可一并移除，它们不影响系统其他部分。
